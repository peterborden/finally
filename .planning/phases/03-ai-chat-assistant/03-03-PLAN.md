  <name>Task 2: Implement app/chat.py and register it in main.py (CHAT-01, CHAT-03, CHAT-04, CHAT-05, CHAT-06)</name>

  <action>
    Create backend/app/chat.py with `from __future__ import annotations`, a module docstring,
    `logger = logging.getLogger(__name__)`, and `router = APIRouter(prefix="/api/chat", tags=["chat"])`
    plus `_USER_ID = "default"` (matching portfolio.py / watchlist.py conventions).

    Request/response models (Pydantic):
    - ChatRequest: message: str.
    - ActionResult: type: Literal["trade", "watchlist"], ticker: str, status: Literal["ok", "error"],
      detail: str, plus optional side/action/quantity/filled_price fields as relevant. This is what the
      response exposes so the LLM's (and validation's) successes/failures are visible to the user.
    - ChatResponseBody: message: str, actions: list[ActionResult].

    create_chat_router() -> APIRouter with `@router.post("")` -> POST /api/chat. Per-request flow
    (mirror the connection handling in portfolio.py: obtain the cache from
    request.app.state.price_cache, market_source from request.app.state.market_source, open one
    connection via get_connection(get_db_path()) and close it in finally):
    1. Load recent history BEFORE inserting the new message: SELECT role, content FROM chat_messages
       WHERE user_id = ? ORDER BY created_at DESC LIMIT a small N (e.g. 20), then reverse to
       chronological order, mapped to [{"role","content"}] dicts.
    2. Build the portfolio-context text: call app.portfolio.build_portfolio(conn, cache) for cash /
       positions (with unrealized P&L and pct_change) / total_value / total_unrealized_pnl, and read
       the watchlist tickers joined with their latest cache prices (reuse the same cache the watchlist
       endpoint uses). Format a concise human-readable context string (CHAT-03).
    3. Persist the user message: INSERT a chat_messages row (uuid hex id, role="user",
       content=message, actions=NULL, created_at=UTC ISO) and commit.
    4. Call app.llm.generate_chat_response(context_text, history, message) -> ChatResponse.
    5. Auto-execute (CHAT-04, CHAT-05), collecting an ActionResult per item, never aborting on one
       failure: for each trade, call app.portfolio.execute_trade(conn, cache, ticker,
       Side(trade.side), trade.quantity) inside try/except TradeError; on success record status="ok"
       with filled_price/quantity, on TradeError record status="error" with the message. For each
       watchlist_change, call the extracted app.watchlist.add_ticker / remove_ticker (await) inside
       try/except Exception; record ok/error. Import Side and TradeError from app.trade_engine and
       execute_trade from app.portfolio — do NOT reimplement any trade math or validation here.
    6. Persist the assistant message: INSERT a chat_messages row with role="assistant",
       content=response.message, actions=json.dumps of the collected ActionResult list, commit.
    7. Return ChatResponseBody(message=response.message, actions=collected).

    Then register the router in backend/app/main.py: import create_chat_router and add
    `app.include_router(create_chat_router())` alongside the other include_router calls — BEFORE the
    static mount (`app.mount("/", StaticFiles(...))`) so /api/chat is never shadowed. Add `__all__` to
    chat.py. Keep Ruff-clean at 100 cols.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client -> POST /api/chat | untrusted user message becomes part of the LLM prompt |
| LLM output -> auto-execution | model-specified trades/watchlist changes act on the portfolio without a confirmation dialog |
| chat handler -> SQLite | user + assistant content and action JSON are written to chat_messages |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-04 | Elevation of Privilege | LLM-driven auto-trades (prompt injection could request trades) | low | accept | Simulated money, single-user, no real funds by design (planning/PLAN.md §9 auto-execution); all trades still pass execute_trade validation (cash/shares) |
| T-03-05 | Tampering | invalid/oversized LLM trade values | medium | mitigate | execute_trade -> apply_trade rejects non-positive qty/price and insufficient cash/shares; failures captured as ActionResult errors, portfolio unchanged |
| T-03-06 | Denial of Service | unbounded chat_messages history growth in the prompt | low | mitigate | History query is LIMIT-bounded (recent N) rather than loading the full log |
| T-03-07 | Information Disclosure | secrets/PII in logs | medium | mitigate | Do not log message content or the API key; follow project logging conventions (no secret dumps) |
</threat_model>
