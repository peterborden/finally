  <action>
    Create a multi-stage Dockerfile at the repo root. Build context is the repo root (needs both frontend/ and backend/).

    Stage 1 — frontend build, base image node:20-slim, name it `frontend-build`:
    - WORKDIR /build.
    - Copy frontend/package.json and frontend/package-lock.json first, run `npm ci` (lockfile exists) — do this before copying the rest of frontend/ so the dependency layer caches across source changes.
    - Copy the remaining frontend/ source, run `npm run build`. next.config.mjs uses output:'export', so this produces /build/out (the static export).

    Stage 2 — runtime, base image python:3.12-slim:
    - Install uv (copy the uv binary from the official ghcr.io/astral-sh/uv image via `COPY --from=ghcr.io/astral-sh/uv:latest /uv /uvx /bin/`, which avoids a curl|sh pipe).
    - WORKDIR /app. Copy backend/pyproject.toml and backend/uv.lock first, then run `uv sync --frozen --no-dev` (installs the locked runtime deps only; dev extras like pytest are not needed at runtime). Then copy the backend/ source (so the code layer invalidates independently of the dependency layer). The backend package root is backend/app, so arrange the copy such that `app` is importable from /app (e.g. copy backend/ contents into /app so /app/app/main.py exists, and run uvicorn with the correct working dir; OR copy backend/app into /app/app and backend/pyproject.toml + uv.lock into /app). Pick one layout and keep it internally consistent with the CMD.
    - Copy the built static export from Stage 1 into the image: `COPY --from=frontend-build /build/out /app/frontend_dist`.
    - ENV FRONTEND_DIST=/app/frontend_dist so app.main serves the real UI.
    - ENV FINALLY_DB_PATH=/app/db/finally.db so the SQLite file lands in the volume mount.
    - Create /app/db in the image (RUN mkdir -p /app/db) so the mount point exists even before the first write.
    - EXPOSE 8000.
    - Add a HEALTHCHECK that GETs http://localhost:8000/api/health (use python's urllib one-liner via `CMD` since curl is not guaranteed in slim; e.g. python -c urllib.request.urlopen). Interval ~30s, start-period ~10s, retries 3.
    - CMD launches uvicorn against the FastAPI app on 0.0.0.0:8000. Use `uv run uvicorn app.main:app --host 0.0.0.0 --port 8000` with the working directory set so `app.main` imports resolve given the copy layout chosen above.

    Do not copy .env into the image and do not bake any local db/finally.db (the .dockerignore from Task 1 enforces this). Keep both stages on slim bases; no dev/test tooling in the runtime stage.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| build context → image | Repo files copied into the image; secrets/local DBs must not be baked in |
| base images / uv binary → runtime | Third-party base images and the uv binary are pulled from registries |
| container filesystem ↔ host volume | /app/db is a mount point crossing the container boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-01 | Information Disclosure | Docker build context | high | mitigate | .dockerignore excludes .env/.env.*, db/*.db, .git, .planning so secrets and local data never enter the image |
| T-05-02 | Tampering | Base images (node:20-slim, python:3.12-slim) + uv | medium | accept | Pin to slim official images and copy uv from the official ghcr image; digest pinning deferred (no lockfile mechanism for base images in scope) |
| T-05-03 | Denial of Service | Container startup | low | mitigate | HEALTHCHECK on /api/health lets the orchestrator detect an unhealthy container instead of routing to a dead process |
| T-05-SC | Tampering | npm ci / uv sync installs | medium | mitigate | Both stages install from committed lockfiles (package-lock.json, uv.lock) with `npm ci` and `uv sync --frozen` — no unpinned resolution; no NEW packages introduced by this plan |
</threat_model>
